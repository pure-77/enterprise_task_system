# Agent 功能增强方案整合与优先级规划

> 来源：用户历史规划（方案 C「规划型 Agent + 总结 + 图表」、方案 D「多模态 + 自动化工作流」）与本轮新增提案（任务分解 / 主动提醒 / 危险确认 / RAG / 组合指令强化）的整合去重。
> 评估维度：**实现复杂度**（技术难度与架构改动量）、**实现成本**（工作量估算）、**实现收益**（实用性 × 功能完备性提升）。
> 现状前提：约 30 个工具已注册（任务/日程/IM/考勤/审批/文件/通知/统计）；意图路由 + SSE 流式 + MySQL 会话持久化已就绪；前端已装 ECharts 5.4.3；后端已有 Celery（含 Beat 定时通道）；QwenVLProvider 已接入。

## 二、方案详情

### 方案 1：任务智能规划与分解（轻量 Plan & Execute）

**目标**：用户说「帮我把今天的任务安排一下」「帮我规划新产品上线准备」，Agent 先输出计划（分步任务清单 / 工具调用链），用户确认后才执行。

**新增能力**：

| 能力 | 说明 | 复杂度 |
| --- | --- | --- |
| 任务分解 | LLM 将大目标拆解为子任务（含优先级、截止日期、建议负责人），生成待确认清单 | 低 |
| 计划确认卡片 | 前端展示可勾选的任务清单，确认后批量创建 | 中 |
| 轻量 Plan & Execute | 计划作为一条特殊工具结果返回，不改造 `service.py` 主循环 | 中 |

**关键改动**：

- 后端：新增 `plan_tasks` 工具（输出结构化计划）；`create_task` 支持批量调用（内部循环复用现有逻辑）
- 提示词：加入分解规则与输出格式约束（JSON Schema）
- 前端：新增「任务计划确认卡片」，复用现有工具卡片渲染管线

**升级路径**：完整版 Plan & Execute（任意多步任务先出 plan 再逐步执行）需改造 `service.py` 主循环加 plan 层，留作方案 2/5 落地后的后续升级。

**评估**：复杂度 中 / 成本 4–6h / 收益 ★★★★★ —— 直接提升任务系统核心体验，是「会调接口 → 会干活」的第一步。

---

### 方案 2：组合指令稳定性强化（地基工程）

**目标**：「创建任务并通知张三，再约明天下午的讨论会」这类多步组合指令稳定一次执行成功。

**关键改动**：

- 意图路由：复合语句返回多个工具组（当前倾向单组或回退全集）
- system prompt 增加组合指令拆解规则 + 3–5 个 few-shot
- 无新架构、无新表、无新接口

**评估**：复杂度 低 / 成本 2–3h / 收益 ★★★★☆ —— 不产生新功能，但它是**所有后续方案的地基**：方案 1 的批量创建、方案 5 的触发器都依赖稳定的多步调用。

---

### 方案 3：危险操作二次确认（安全闭环）

**目标**：`danger` 级工具（删除文件、驳回审批、删除日程）执行前暂停，前端弹出确认卡片，用户点「确认/取消」后继续；30s 超时自动取消。

**关键改动**：

- 后端：工具执行引入「待确认」中断态（Redis 存 pending action，key = `confirm:{session_id}:{tool_call_id}`）；新增确认回传接口 `POST /agent/confirm`
- SSE：增加 `confirm_request` 事件类型
- 前端：确认卡片 UI（复用 danger_level 红色边框样式）

**评估**：复杂度 中 / 成本 4–6h / 收益 ★★★★☆ —— 防 Agent 误删误批，**多人使用前必做**的安全刚需。

---

### 方案 4：数据洞察：一键总结 + 图表生成

**目标**：从「调接口取数据」升级为「主动给洞察」。

**新增能力**：

| 能力 | 说明 | 复杂度 |
| --- | --- | --- |
| `summarize_today_work` | 聚合当日任务完成/考勤/日程 → LLM 组织语言 | 中 |
| `summarize_week_progress` | 聚合本周进展（任务完成率、逾期项、打卡情况） | 中 |
| `summarize_task_status` | 指定范围任务状态分布总结 | 中 |
| `generate_chart` | 后端输出 ECharts option JSON，前端直接渲染 | 中 |

**技术选型（图表）**：

| 方案 | 结论 |
| --- | --- |
| **ECharts JSON 前端渲染** | ✅ 选用。前端已装 echarts 5.4.3，交互式图表体验最好，零后端新依赖 |
| matplotlib 静态图 | ❌ 无交互、引入图片存储与依赖 |
| Mermaid | ❌ 适合流程图，不适合数据统计图 |

**关键改动**：

- 后端：新增 `summary_tools.py`（3 个聚合查询工具，纯 SELECT 不做写操作）+ `generate_chart`（输出 ECharts option）
- 前端：Agent 消息渲染管线识别 `chart` 类型结果 → 挂载 ECharts 组件

**评估**：复杂度 中 / 成本 6–10h / 收益 ★★★★☆ —— 产品差异化亮点，用户感知最强的「智能感」来源。

---

### 方案 5：主动服务：定时提醒 + 自动化触发器 + 日报/周报

**目标**：Agent 从「被动响应」升级为「主动服务」。

**新增能力**：

| 能力 | 说明 | 复杂度 |
| --- | --- | --- |
| 对话式提醒 | 「明天下午3点提醒我交周报」→ 持久化定时任务，到点经 WebSocket + 通知中心推送 | 中 |
| 定时日报/周报 | 每天 18:00 / 每周五自动拉取数据 → LLM 写总结 → 推送给用户 | 中 |
| 事件触发器 | 「有新审批时自动通知我」「任务逾期提醒」—— 业务事件桥接 Agent | 高 |

**关键改动**：

- 新增 `reminder` 表（user_id / workspace_id / trigger_time / payload / status）
- **复用现有 Celery + Beat**（`app/core/celery_config.py` + `app/tasks/`），不引入 APScheduler，省去新中间件
- 新增工具：`create_reminder` / `list_reminders` / `cancel_reminder`
- 事件触发器：在审批/任务模块的状态变更处发 Celery 任务 → 调 Agent 总结 → 走通知通道

**评估**：复杂度 中高 / 成本 8–12h（复用 Celery 后从 15h+ 下调）/ 收益 ★★★★★ —— 用户感知最强的能力质变，但依赖方案 2 的多步稳定性，故排 P2。

---

### 方案 6：多模态增强：图片理解 + 语音输入输出

**新增能力**：

| 能力 | 说明 | 复杂度 |
| --- | --- | --- |
| `analyze_image` / `ocr_document` | QwenVLProvider 已接入，暴露为工具即可：截图描述、票据/文档 OCR | **低** |
| 语音输入 | 浏览器 Web Speech API 录音转文字（零依赖），Whisper 作为可选升级 | 中 |
| 语音输出 | 浏览器 speechSynthesis 朗读 Agent 回复（零依赖） | 低 |

**关键改动**：

- 图片：新增 2 个工具，handler 内部调 `QwenVLProvider`；多模态消息契约此前已修复（OpenAI content parts 格式），工作量小
- 语音：纯前端能力（Web Speech API），后端零改动；Whisper/TTS 服务化留作后续升级

**评估**：图片理解 复杂度 低 / 成本 3–5h / 收益 ★★★☆☆（场景触发频率中）；语音 复杂度 中高 / 成本 6–10h / 收益 ★★★☆☆ —— 图片理解性价比高可提前，语音属于锦上添花。

---

### 方案 7：文件知识问答（RAG）

**目标**：对文件中心文档、公告、IM 历史消息建向量索引，支持「上次公告里的放假安排」「张三发的需求文档讲了什么」等语义问答。

**关键改动**：

- 向量存储：**轻量 Chroma 本地嵌入式起步**（避免 pgvector/Milvus 的新中间件运维成本），数据量上去后可迁移
- embedding：远端 API（与现有 LLM 供应商对齐）
- 文件上传/公告发布时异步切片入库（挂 Celery 任务）
- 新增 `query_file_content` 工具，检索结果注入上下文；**检索必须按 workspace_id + 成员权限过滤**

**评估**：复杂度 高 / 成本 12–20h（文件解析 PDF/Office、切片策略、权限过滤、检索调优均为新领域）/ 收益 ★★★★☆ 长期最高，短期中 —— 个人/小团队场景触发频率有限，建议作为长期规划。

## 三、实施路线（推荐顺序）

```
阶段一（P0）：方案 2 → 方案 1
  先打地基（多步调用稳定），再上任务规划分解。两者合计 6–9h，
  落地后 Agent 即具备「一句话规划一组任务」的核心卖点。

阶段二（P1）：方案 3 → 方案 4
  安全闭环（多人使用前提）+ 数据洞察（差异化亮点）。

阶段三（P2）：方案 5 → 方案 6·图片理解
  主动服务依赖阶段一的多步稳定性；图片理解成本低顺带做。

阶段四（P3）：方案 7（RAG）→ 方案 6·语音
  长期能力，按实际使用频率决策投入。
```

**依赖关系**：

- 方案 1、5 依赖方案 2（多步调用稳定性）
- 方案 4 的周报可被方案 5 的定时触发器复用（先有人工总结，后有自动推送）
- 方案 6·语音 与所有方案正交，可随时插入
- 方案 7 独立，但建议方案 4 落地后再做（总结能力可复用到检索结果组织）

**若只做一项**：方案 1（投入产出比最高）。
**上线多人前最低要求**：方案 2 + 3 + 4。
